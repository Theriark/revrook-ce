# Changelog

All notable changes to revrook CE are recorded in this file. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project will follow [Semantic Versioning](https://semver.org/) once it has a release.

No version has been released: there is no tag, no GitHub release and no published image. Everything below is under Unreleased and describes the release candidate that the Development environment runs. The version in `pyproject.toml` stays `0.0.0.dev0` until a release is authorised ([docs/release-candidate.md](docs/release-candidate.md)).

## [Unreleased]

### Added

- Repository, container and CI foundations: a multi-stage non-root image, a compose stack (web, worker, PostgreSQL 16), hashed requirement files, the nine-check merge gate and the licence audit.
- Sign-in with Argon2id, signed session cookies, CSRF protection, API tokens, an append-only audit trail and strict response headers.
- An evidence store: content-addressed files, immutable revisions, assurance labels, a hash chain with a verify command, per-client pseudonymisation, retention and deletion per client.
- Importers for Microsoft 365 exports (identity, secure score, devices, conditional access, directory roles) and for generic device, backup, network, training, leaver and mail exports, with a profile editor for files whose columns have other names.
- A library of 51 controls with plain-language wording, the check engine (automatic rules, manual alternatives, exceptions register) and the NIST CSF 2.0 and SP 800-171 reference names.
- The scoring engine: exact rational scores with a lower and an upper bound, freshness decay, gate caps, coverage, ruleset versions and stored snapshots that regenerate byte for byte.
- A public DNS check for SPF, DKIM and DMARC that stores a failed lookup as unknown and never as a fail.
- Reports made from a stored snapshot: the quarterly security review and the cyber insurance evidence pack, each as one HTML file with print styles, a disclaimer on every page and an export history that keeps an immutable copy and its SHA-256.
- The web interface: clients, overview, checklist, control drawer, evidence and imports, exceptions, report builder, export history, settings and a glossary.
- Operations: a scheduler, expiry reminders by mail, retention purge, a full data export without personal identifiers, deletion per client, optional Prometheus metrics, a system page with a stale-worker banner, an optional outside heartbeat, and a backup and restore guide with a script that proves a restore.
- Extension API version 1 with seven extension points and plugin loading through an entry point group ([docs/extension-api.md](docs/extension-api.md)).
- Documentation: quick start, install, configuration, upgrade, security review and a mapping policy, with an index in the README. `scripts/demo.sh` loads one synthetic client so that a new installation has something to look at.
- `verify-mappings` command: lists the mapping rows nobody has verified, checks every NIST identifier against the pinned names extract (a consistency check against the 32 CSF and 26 SP 800-171 identifiers transcribed from the catalog at the recorded commit; it is not a comparison with the full catalog) and keeps the register of verified rows equal to the control file.
- An upgrade test that seeds a database at each earlier schema revision, upgrades it to the newest and checks that no row is lost.
- `tests/test_docs.py`: links between pages, the configuration table against the settings, the README statements and the format of this file.

### Changed

- The web interface has a design system ([docs/design-system.md](docs/design-system.md)): tokens for colour, type, spacing and radius; an app shell with a charcoal navigation rail, grouped links with icons and the signed-in user; redesigned sign-in and first-run pages with the logo at a proper size; and the buttons, fields, tables, cards, status pills, alerts, empty states, import area and confirmation patterns the other pages will adopt. No behaviour, data or evidence rule changed.
- Home is a dashboard of every client ([docs/design-system.md](docs/design-system.md), Dashboard): four stat cards with sparklines from the stored reports, a posture ring per client, the most urgent controls across all clients, the scores of the last 90 days, the controls by domain and the recent changes of the audit trail. It reads the same views and snapshots as the client pages and the reports; nothing is stored and no behaviour, data or evidence rule changed.
- The clients list and the client overview follow the design system ([docs/design-system.md](docs/design-system.md), Clients). The list shows each client's last stored report as a posture ring with its band, the controls of that report by status as pills with counts, the newest evidence with its age, and has a search, filter chips with counts, sortable headings, a comfortable or compact density, fifty rows a page and stacked cards on a phone; the posture is read from the stored snapshot with the scoring the report used, never from a check run on the list. The overview has a client header with the way back and two actions, a large posture ring with the band, coverage and the summary, the controls by status as a bar, what needs attention for this client, the coverage by domain as bars with weight and score, the evidence freshness and the recent changes of this client. No behaviour, data or evidence rule changed.
- The checklist and the control page follow the design system ([docs/design-system.md](docs/design-system.md), Checklist and control detail). The checklist has a filter band with two chips and their counts, a table whose head stays in view, the flags of a row as a short list, a violet mark on a row whose status changed since the last report, card rows on a phone and an empty state for a quiet filtered view. The control page opens with a verdict band (the status as a large pill beside the evidence facts), then what was checked and the exceptions beside the notes card, whose suggested wording sits on the canvas and which shows "Saving" while a note is posted. No behaviour, data or evidence rule changed.
- The evidence page, the profile editor and the integrity check follow the design system ([docs/design-system.md](docs/design-system.md), Evidence imports). The evidence page opens with an evidence verdict (the state of the client's evidence as one pill beside the sources, the current ones, the ones to refresh and the items imported), then the exports to refresh as a numbered list in the order to work in, the sources and everything imported as tables that become cards on a phone, and an empty state that leads to the profile editor. The profile editor is five numbered step cards with the drag-and-drop import area, an indicator beside every button while a file is read, saved or imported, help texts on the profile name and the capture time, an import result card and empty states for a missing client, a file without rows and a source without a saved profile. The integrity page starts with the check as its one action, then shows the verdict (all chains intact, or how many are broken) with the records and the time of the check, the table of chains with a mark on a broken one, and what the check proves. No behaviour, data or evidence rule changed.
- The exceptions register, the report builder, the report page, the export history, the settings, the system page, the glossary and the problem page follow the design system ([docs/design-system.md](docs/design-system.md), Exceptions and reports). The register opens with a verdict (how many exceptions are open and overdue, the next review date) over a table that becomes cards on a phone, and the form to add one is a card with help on each field. The builder is three numbered step cards and shows "Saving" while the details are posted. The report page shows the export as a paper sheet on the canvas, the cover facts and the summary drawn as the client receives them, beside the readiness verdict, the problems to fix first and the two reports with their preview and export. The export history breaks a file name or a digest inside its card. Settings and System open with the page header; the fixed facts of the installation are cards, the worker is a verdict band, the services a list of pill and sentence, and a client is deleted behind the inline confirmation with the danger button. The glossary is one card with each term beside its meaning, and a refusal (404, 409, 422) is one card with the status code as a figure, the message, the details and two ways back. No behaviour, data or evidence rule changed.
- The stylesheets and scripts are linked with a version query (`?v=` and a digest of the four files, `asset_version()` in `app/ui/brand.py`), so a new version of a file has a new address and a browser or a cache in front of the installation never serves an old stylesheet with a new page after an upgrade.
- `docs/operations.md` states how request bodies are framed: a body must declare its size in `Content-Length`, and any `Transfer-Encoding` is answered with 411.
- The compose smoke test runs the quick start (`scripts/e2e/phase_11.sh`) and fails if it takes ten minutes or more. The script is for CI only: it leaves a fixed-password administrator account behind, so the quick start does not tell users to run it.

### Fixed

- From the code review of that follow-up: below 1024 px the fade of the navigation bar stayed over the last link for the last 16 px of scrolling, because the bar keeps that much end padding after the space that ends the strip, so the shell script now counts the end padding of each strip; the message after adding or closing an exception or saving the details of a report is read out by a screen reader (the script moves focus to it) and its query (`?done=`, `?saved=`) is taken out of the address so a reload does not repeat it, while without script the redirect and the message are as before; and the problem page logs one warning with the class of the error when the database cannot say who is signed in (it was silent).
- From the follow-up of that retest: the fade at the edge of the navigation bar and of the client tabs reaches its colour within 20 px, the strip ends in space as wide as the fade and the shell script hides the fade while nothing lies to the right of what is in view (at 768 px the tabs showed a fade with every tab in view and the cut link of the navigation got a faint cue); a link that keyboard focus scrolls into view stops clear of the fade; adding or closing an exception and saving the details of a report without script show a message after the redirect; the export history and the schedules are cards below 1024 px, so a file name, a SHA-256 or a cron expression no longer breaks into columns of six letters at 768 px; the summary of an opened delete disclosure is white on charcoal (Pico coloured it grey, and on a touch screen the hover stays after the tap); an address no page answers is still the problem page when the database is down (it was a 500); and `/api` without a slash keeps the JSON refusal like `/api/`. The new rules are in `app/static/css/revrook-retest.css`, loaded after `revrook.css`.
- From the retest of the web interface at 1440, 768 and 390 px: the clients list broke the band of the last report one letter a line at 768 px and pushed the page sideways, so its rows are cards below 1024 px (two to a row from 768 px) and the row actions wrap beside the sidebar until 1280 px; an address no page answers, or a method a page does not take, was raw JSON and is now the problem page (the API, the probes and the static files keep JSON); the result of an import names the controls that read the export and says that the others keep their status until their own export is imported, and that the score on the clients list and on Home comes from the newest report; the summary of a details element had no visible focus ring (Pico's rule outranked the design rule); the navigation bar and the client tabs scroll sideways below 1024 px with the last visible link fading at the edge as the cue; the trend chart has a narrow drawing with a legend for a phone, and a stack of line labels is kept off the dates of the axis. Also from the retest: the profile editor shows step 3 even when the file is refused, so the numbers never skip, and opens on the client it was called for from the evidence and control pages.
- On the clients list and the client overview on Development, Pico CSS gave every submit button the width of its form: the Search button spanned the toolbar beside a 54 px search box, and "Show this period" and "Add client" spanned their cards. A button is now as wide as its words on every page (the sign-in button and the sign-out button of the rail still take the whole line, and the add form's button does on a phone). The filter chips carried Pico's square list marker; a status pill in the narrow cell of the evidence freshness table broke "Not imported" one letter a line, so a pill stays on one line and the domains and the freshness share their row evenly from 1280 px; and on a phone the caption of the clients list shrank to one word a line.
- On Home the table of controls by domain was wider than its card and pushed the page sideways at 1440 and 390 px. The breakdown is now one stacked bar per domain across the card with the protected share beside the name, and every count sits in a table under "Show the numbers" that scrolls inside the card on a phone. The four stat cards stand one, two or four to a row (never three and one), the trend chart and the breakdown share one height with an empty state centred in it, and a posture ring card is wide enough for a client name of about twenty letters.
- The arrow of a select, the date picker icon and the check mark of a checkbox were `data:` images of Pico CSS, which the content security policy blocks; the native controls are shown instead and the stylesheet loads no image at all.
- In the app shell on a narrow phone the "Community Edition" badge overlapped the sign-out button, and in the rail the signed-in name was cut short beside that button: the badge is hidden below 600 px (the footer names the edition) and the button has its own line in the rail. The sign-in tagline grows to 24 px only from 1024 px, where the panel is wide enough for it.
- A request with `Transfer-Encoding: chunked` and a small `Content-Length` passed the body size check; any `Transfer-Encoding` is now refused with 411.
- A plugin that fails to load no longer chains its own error into the message; only its name and the class of the error are reported.
- A bearer token on a page no longer skips the CSRF check; only paths under `/api/` do.
- An API id past 2^63 - 1 gave a 500; it is now refused with 422.

### Security

- The security checklist of phase 11 was run and is in [docs/security-review.md](docs/security-review.md): no finding of High or Medium severity is open. Fixed: parallel sign-ins could use up the database connections, request bodies other than uploads had no size cap and the data export was built whole in memory.
- Scores are uncalibrated design choices and mappings to outside frameworks are unverified unless marked; nothing in revrook is a certification.
